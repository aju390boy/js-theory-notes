Part 1

🌱 The Basics

Master the foundational commands. Every professional Git workflow starts here — these are the commands you'll use every single day.

🗂️
git init
Initialize

Creates a brand-new Git repository in your current directory. This generates a hidden .git/ folder that tracks all your project's history, branches, and configuration. Every Git project starts here — think of it as the "big bang" of your repository.

bash
1# Initialize a new repo in the current directory 2git init 3 4# Initialize in a specific folder (creates it if absent) 5git init my-project 6 7# Initialize with a specific default branch name (modern style) 8git init --initial-branch=main 9 10# Set default branch globally (do this once) 11git config --global init.defaultBranch main
💡
Industry Tip: Always use main as your default branch (not master). Set it globally once with the config command above and all future repos will use main automatically.
📥
git clone
Clone

Downloads a remote repository (GitHub, GitLab, Bitbucket, etc.) to your local machine — including all its history, branches, and tags. This is how you start working on any existing project.

bash
1# Clone via HTTPS (most common) 2git clone https://github.com/user/repo.git 3 4# Clone via SSH (preferred for contributors with key setup) 5git clone git@github.com:user/repo.git 6 7# Clone into a custom folder name 8git clone https://github.com/user/repo.git my-folder 9 10# Shallow clone — only latest snapshot (faster, less disk) 11git clone --depth 1 https://github.com/user/repo.git 12 13# Clone a specific branch only 14git clone --branch develop --single-branch https://github.com/user/repo.git
FlagDescription
--depth <n>Fetch only last n commits (great for CI pipelines)
--branch <name>Clone a specific branch
--single-branchOnly clone the specified branch's history
--recurse-submodulesAlso clone nested submodules
--bareClone without working directory (server-side repos)
🔍
git status
Inspect

Shows the current state of your working directory and staging area. It tells you what's changed, what's staged for the next commit, and what's untracked. You'll run this command dozens of times per day.

bash
1git status 2 3# Short/compact output — beloved by pros 4git status -s 5 6# Show branch info in short format 7git status -sb 8 9# Sample output (short format) 10M src/app.js # M = modified (staged) 11 M src/index.js # space M = modified (not staged) 12?? newfile.txt # ?? = untracked 13A styles/main.css # A = newly added (staged)
➕
git add
Stage

Stages changes — moves them from your working directory into the staging area (index). Only staged changes are included in the next commit. This gives you precise control over what goes into each commit.

bash
1# Stage a specific file 2git add src/app.js 3 4# Stage an entire folder 5git add src/ 6 7# Stage ALL changes (new + modified + deleted) 8git add . 9 10# Stage all tracked modified/deleted (NOT new files) 11git add -u 12 13# Interactively choose which HUNKS to stage (powerful!) 14git add -p src/app.js 15 16# Stage all files matching a pattern 17git add *.js
ℹ️
Pro Technique — Patch Mode (-p): Instead of staging an entire file, git add -p lets you review and choose individual "hunks" (chunks of changes). This is the industry standard for creating clean, atomic commits. Press y to stage, n to skip, s to split.
💾
git commit
Commit

Takes a snapshot of all staged changes and saves it permanently in the repository history with a unique SHA-1 hash. Each commit is a permanent, immutable record of your project at that point in time.

bash
1# Standard commit with message 2git commit -m "feat: add user authentication" 3 4# Stage all tracked + commit in one step 5git commit -am "fix: correct login redirect URL" 6 7# Amend the LAST commit (change message or add forgotten files) 8git commit --amend -m "feat: add user authentication module" 9 10# Amend without changing message (just add staged files) 11git commit --amend --no-edit 12 13# Commit with extended body message (opens editor) 14git commit 15 16# Empty commit (useful for triggering CI pipelines) 17git commit --allow-empty -m "chore: trigger CI rebuild"
📏 Conventional Commits — Industry Standard
commit message format
feat: a new feature fix: a bug fix docs: documentation only changes style: formatting, no logic change refactor: code change, not fix or feature test: adding missing tests chore: build process, dependency updates BREAKING CHANGE: incompatible API change # Examples: feat(auth): add OAuth2 Google login fix(api): handle null response in user endpoint docs: update README with setup instructions
🚀
git push
Publish

Uploads your local commits to the remote repository (GitHub). This makes your work visible to teammates and backs it up in the cloud.

bash
1# Push current branch to origin 2git push 3 4# Push and set remote tracking (first push of new branch) 5git push -u origin feature/login 6 7# Push a specific branch 8git push origin main 9 10# Push all branches 11git push --all origin 12 13# Push tags to remote 14git push --tags 15 16# Force push (DANGER: rewrites remote history!) 17git push --force-with-lease # safer than --force 18 19# Delete a remote branch 20git push origin --delete feature/old-branch
⚠️
Never use --force on shared branches! Always prefer --force-with-lease — it checks that nobody else has pushed since your last fetch, preventing accidental overwrites of teammates' work.
⬇️
git pull
Sync

Fetches remote changes AND immediately merges them into your current branch. Essentially git fetch + git merge in one command. Use this to stay in sync with your team's work.

bash
1# Standard pull (fetch + merge) 2git pull 3 4# Pull with rebase instead of merge (cleaner history!) 5git pull --rebase 6 7# Pull from a specific remote and branch 8git pull origin main 9 10# Set pull to always rebase (configure once) 11git config --global pull.rebase true
💡
Best Practice: Use git pull --rebase instead of plain git pull. This keeps your local commits on top of the upstream changes, giving you a linear, clean history instead of messy merge commits.
📡
git fetch
Download

Downloads remote changes but does NOT merge them. It updates your remote-tracking branches (like origin/main) so you can inspect what changed before deciding to integrate it. This is the safe way to check on remote changes.

bash
1# Fetch all remotes 2git fetch 3 4# Fetch from a specific remote 5git fetch origin 6 7# Fetch a specific branch 8git fetch origin main 9 10# Fetch and prune deleted remote branches 11git fetch --prune 12 13# After fetch, see what changed vs your local 14git log HEAD..origin/main --oneline
📜
git log
History

Displays the commit history of your repository. By default it shows commits in reverse chronological order. With various flags, it becomes an extremely powerful tool for code archaeology and understanding project evolution.

bash
1# Basic log 2git log 3 4# Compact one-line format (most used) 5git log --oneline 6 7# Gorgeous graph view — see branches & merges 8git log --oneline --graph --decorate --all 9 10# Custom format (author, date, message) 11git log --pretty=format:"%h %an %ar - %s" 12 13# Last N commits only 14git log -10 --oneline 15 16# Filter by author 17git log --author="Alice" 18 19# Filter by date range 20git log --since="2024-01-01" --until="2024-12-31" 21 22# Search commit messages with grep 23git log --grep="authentication" --oneline 24 25# Show commits that changed a specific file 26git log --follow --oneline src/app.js 27 28# Show files changed in each commit 29git log --stat --oneline
💡
Power Alias: Add this to your git config: git config --global alias.lg "log --oneline --graph --decorate --all". Then just type git lg for a beautiful branch tree!
🔀
git diff
Compare

Shows the exact line-by-line changes between commits, branches, or your working directory. Essential for code review and understanding what has changed before committing.

bash
1# Unstaged changes (working dir vs index) 2git diff 3 4# Staged changes (what will go into next commit) 5git diff --staged 6 7# Diff between two branches 8git diff main..feature/login 9 10# Diff between two commits (use hashes from git log) 11git diff abc1234..def5678 12 13# Show only which files changed (not the lines) 14git diff --name-only main..feature 15 16# Show word-level diff (easier to read) 17git diff --word-diff
🌿
git branch
Branch

Lists, creates, renames, and deletes branches. Branches are lightweight movable pointers to specific commits. They let multiple features be developed simultaneously without interfering with each other.

bash
1# List local branches (* = current branch) 2git branch 3 4# List all branches (local + remote) 5git branch -a 6 7# List remote branches only 8git branch -r 9 10# Create a new branch 11git branch feature/user-profile 12 13# Rename current branch 14git branch -m old-name new-name 15 16# Delete a merged branch 17git branch -d feature/done 18 19# Force delete (even if unmerged) 20git branch -D feature/abandoned 21 22# Show merged branches (safe to delete these) 23git branch --merged 24 25# Show unmerged branches (be careful deleting) 26git branch --no-merged
🔄
git checkout / git switch
Navigate

Switches between branches or restores files. git switch is the modern replacement for git checkout (branch operations only), introduced in Git 2.23 to reduce confusion. Both are used in industry today.

bash
1# Switch to an existing branch (modern) 2git switch develop 3 4# Create AND switch in one command (modern) 5git switch -c feature/payment-api 6 7# Create branch from a specific base 8git switch -c feature/new main 9 10# --- Old style (still widely used) --- 11git checkout develop 12git checkout -b feature/payment-api 13 14# Restore a file to its last committed state (discard changes) 15git checkout -- src/app.js 16 17# Jump to a specific commit (detached HEAD state) 18git checkout abc1234 19 20# Checkout a remote branch locally 21git checkout -t origin/feature/api-v2
🔗
git merge
Merge

Integrates changes from one branch into another. Git offers multiple merge strategies. Understanding when to use each type is a key sign of an experienced developer.

bash
1# Merge a branch into current branch (creates merge commit) 2git merge feature/login 3 4# Fast-forward merge (no merge commit if possible) 5git merge --ff-only feature/login 6 7# Always create a merge commit (no fast-forward) 8git merge --no-ff feature/login 9 10# Squash all commits into one, then commit manually 11git merge --squash feature/login 12git commit -m "feat: complete login feature" 13 14# Abort a merge in progress (if conflicts) 15git merge --abort
🔀 Merge Strategies Compared
StrategyUse WhenResult
--ffLinear history, no divergenceNo merge commit (moves pointer)
--no-ffFeature branches (GitHub default)Always creates a merge commit
--squashClean up messy WIP commitsOne commit on target branch
🌐
git remote
Remote

Manages the remote connections of your repository. A "remote" is a named reference to a remote repository URL. origin is the conventional name for the primary remote.

bash
1# List all remotes 2git remote -v 3 4# Add a new remote 5git remote add origin https://github.com/user/repo.git 6 7# Change the URL of an existing remote 8git remote set-url origin git@github.com:user/repo.git 9 10# Rename a remote 11git remote rename origin upstream 12 13# Remove a remote 14git remote remove upstream 15 16# Show detailed info about a remote 17git remote show origin
ℹ️
Fork Workflow Pattern: When contributing to open-source, add two remotes: origin (your fork) and upstream (the original repo). Fetch from upstream, push to origin, then submit PRs.

git config
Configure

Sets Git configuration values at system, global (user), or local (project) level. Always set your name and email first — these are recorded in every commit you make.

bash
1# === ESSENTIAL FIRST-TIME SETUP === 2git config --global user.name "Your Name" 3git config --global user.email "you@example.com" 4git config --global core.editor "code --wait" # VS Code as editor 5 6# Set default branch name globally 7git config --global init.defaultBranch main 8 9# Auto-correct typos (wait 2s before applying) 10git config --global help.autocorrect 20 11 12# Always pull with rebase 13git config --global pull.rebase true 14 15# List all current settings 16git config --list 17 18# View the global config file directly 19git config --global --edit
🙈
.gitignore
Ignore Files

A special file that tells Git which files and directories to permanently ignore (never track). Essential for keeping secrets, build artifacts, dependencies, and OS-generated files out of your repository.

.gitignore
# Dependencies node_modules/ vendor/ # Build outputs dist/ build/ *.min.js # Environment & secrets — NEVER commit these! .env .env.local .env.production *.pem *.key # OS files .DS_Store Thumbs.db # Editor files .vscode/ .idea/ # Logs *.log logs/ # Ignore all .txt files in a folder docs/*.txt # But track this specific file !docs/important.txt
bash — useful gitignore commands
# Check if a file is being ignored git check-ignore -v node_modules/ # Remove a file from tracking (but keep it locally) git rm --cached .env # Remove folder from tracking git rm -r --cached node_modules/
💡
Visit gitignore.io to auto-generate .gitignore files for your specific tech stack (Node, Python, React, Java, etc.)

⚡ Advanced

Level up your Git skills with powerful tools used by senior engineers daily — rewriting history, recovering from mistakes, and managing complex collaboration workflows.

🔧
git rebase
Rewrite History

Reapplies commits from one branch on top of another, creating a clean, linear history. Unlike merge (which creates merge commits), rebase rewrites commit hashes and produces a cleaner commit graph. It's one of the most powerful and nuanced Git operations.

bash
1# Rebase current branch onto main 2git rebase main 3 4# === INTERACTIVE REBASE — most powerful tool === 5# Edit last 5 commits (squash, reorder, edit messages) 6git rebase -i HEAD~5 7 8# Rebase against main's latest 9git rebase -i origin/main 10 11# Abort an in-progress rebase 12git rebase --abort 13 14# Continue after resolving conflicts 15git rebase --continue 16 17# Skip the current conflicting commit 18git rebase --skip
✏️ Interactive Rebase Commands (in Editor)
rebase todo file
pick abc1234 feat: add login form # keep as-is squash def5678 fix: typo in login # squash into previous fixup ghi9012 WIP remove debug log # squash, discard message reword jkl3456 add tests # keep but edit message drop mno7890 temp debugging commit # completely remove edit pqr1234 refactor auth module # pause to amend this commit
⚠️
Golden Rule: Never rebase commits that have been pushed to a shared remote branch. Rebase rewrites commit hashes — if teammates have pulled those commits, it creates chaos. Only rebase your local, unpublished commits.
📦
git stash
Save State

Temporarily shelves changes you've made to your working directory so you can switch context quickly without committing half-done work. Think of it as a clipboard for your code changes.

bash
1# Stash current changes 2git stash 3 4# Stash with a descriptive name 5git stash push -m "WIP: payment form validation" 6 7# Also stash untracked files 8git stash -u 9 10# Stash including ignored files 11git stash -a 12 13# List all stashes 14git stash list 15 16# Apply most recent stash (keeps it in stash list) 17git stash apply 18 19# Apply AND remove from stash list (pop) 20git stash pop 21 22# Apply a specific stash by index 23git stash apply stash@{2} 24 25# Show changes in a stash 26git stash show -p stash@{0} 27 28# Create a new branch from a stash 29git stash branch feature/from-stash stash@{0} 30 31# Delete a specific stash 32git stash drop stash@{1} 33 34# Clear ALL stashes 35git stash clear
🍒
git cherry-pick
Select Commits

Applies one or more specific commits from another branch onto the current branch. It's like saying "I want that exact change from that branch, but not the whole branch." Widely used in hotfix workflows.

bash
1# Apply a single commit by hash 2git cherry-pick abc1234 3 4# Cherry-pick a range of commits 5git cherry-pick abc1234..def5678 6 7# Cherry-pick without committing (stage only) 8git cherry-pick -n abc1234 9 10# Abort a cherry-pick with conflicts 11git cherry-pick --abort 12 13# Continue after resolving conflicts 14git cherry-pick --continue
🔥 Real-World Scenario: Hotfix to Production
bash — hotfix workflow
# Bug fixed on develop (commit hash: a3f9b2c) # Need it on production branch NOW without merging all of develop git switch production git cherry-pick a3f9b2c git push origin production # Bug is now in production — crisis averted! 🎉
⏮️
git reset
Undo Changes

Moves the HEAD pointer (and optionally the working directory) backwards to a previous state. Unlike git revert, reset actually removes commits from history. Understand the three modes well — they have very different effects.

bash
1# --- THREE MODES --- 2 3# SOFT: Move HEAD back, keep changes staged 4git reset --soft HEAD~1 5 6# MIXED (default): Move HEAD back, unstage changes, keep files 7git reset HEAD~1 8 9# HARD: Move HEAD back, DISCARD all changes (destructive!) 10git reset --hard HEAD~1 11 12# Unstage a file (without losing changes) 13git reset HEAD src/app.js 14 15# Reset to a specific commit hash 16git reset --hard abc1234 17 18# Reset to match remote main exactly 19git reset --hard origin/main
ModeHEADStaging AreaWorking Dir
--soft✓ MovedUnchanged (staged)Unchanged
--mixed✓ Moved✓ ClearedUnchanged
--hard✓ Moved✓ Cleared✓ Discarded
↩️
git revert
Safe Undo

Creates a new commit that undoes the changes of a previous commit, without removing it from history. This is the safe way to undo on shared branches — it doesn't rewrite history, so it's safe to push to remote.

bash
1# Revert the last commit (creates a new "undo" commit) 2git revert HEAD 3 4# Revert a specific commit by hash 5git revert abc1234 6 7# Revert without auto-committing (stage only) 8git revert --no-commit abc1234 9 10# Revert a range of commits 11git revert abc1234..def5678
ℹ️
reset vs revert: Use git reset when undoing local, unpushed commits. Use git revert when undoing commits on a shared branch — it preserves history integrity and is safe for team collaboration.
🏷️
git tag
Releases

Creates permanent labels on specific commits — used to mark release versions. Unlike branch names, tags don't move as new commits are added. Standard practice is to use Semantic Versioning: v1.2.3.

bash
1# List all tags 2git tag 3 4# Create a lightweight tag on current commit 5git tag v1.0.0 6 7# Create an annotated tag (recommended — stores author, date, message) 8git tag -a v1.0.0 -m "Release: v1.0.0 — stable production release" 9 10# Tag a specific commit 11git tag -a v0.9.0 abc1234 -m "Beta release" 12 13# Push a specific tag to remote 14git push origin v1.0.0 15 16# Push all tags 17git push origin --tags 18 19# Delete a tag locally 20git tag -d v1.0.0 21 22# Delete a remote tag 23git push origin --delete v1.0.0 24 25# Checkout code at a specific tag 26git checkout v1.0.0
🕐
git reflog
Recovery

The safety net of Git. Reflog records every movement of HEAD, including resets, rebases, and branch switches. Even after a destructive git reset --hard, you can use reflog to recover "lost" commits. This has saved thousands of developers from disaster.

bash
1# Show full reflog 2git reflog 3 4# Sample reflog output: 5abc1234 HEAD@{0}: reset: moving to HEAD~2 6def5678 HEAD@{1}: commit: feat: add payment page 7ghi9012 HEAD@{2}: commit: fix button styles 8 9# Recover a "lost" commit by resetting to it 10git reset --hard def5678 11 12# Or create a new branch from the lost commit 13git branch recovery-branch def5678 14 15# Reflog for a specific branch 16git reflog show feature/login
💡
Remember: Reflog is local only — it's not pushed to remote. By default, reflog entries expire after 90 days. So act quickly after an accidental reset!
🔬
git bisect
Debug

Uses binary search to find the exact commit that introduced a bug. Instead of manually checking every commit, Git automatically narrows it down — checking O(log n) commits instead of all n. Invaluable for debugging regressions.

bash
1# Start bisect session 2git bisect start 3 4# Mark current state as BAD (bug is present) 5git bisect bad 6 7# Mark a known GOOD commit (bug wasn't there yet) 8git bisect good v2.0.0 9 10# Git checks out the midpoint — test it, then mark: 11git bisect good # or 12git bisect bad 13 14# Git narrows down — repeat until it finds the commit! 15abc1234 is the first bad commit 16 17# End the session (restores original branch) 18git bisect reset 19 20# AUTOMATED bisect with a test script! 21git bisect start 22git bisect bad HEAD 23git bisect good v2.0.0 24git bisect run npm test # runs test on each commit automatically

bash

git clean
Cleanup

Removes untracked files and directories from your working directory. Useful for cleaning up build artifacts, generated files, or test outputs without affecting committed files.

bash
1# Preview what would be deleted (dry run — ALWAYS do this first!) 2git clean -n 3 4# Remove untracked files (requires -f to force) 5git clean -f 6 7# Remove untracked files AND directories 8git clean -fd 9 10# Also remove ignored files (full nuclear clean) 11git clean -fdx 12 13# Interactive mode — choose what to remove 14git clean -i
⚠️

git submodule
Dependencies

Allows you to include and track another Git repository inside your repo as a dependency. Each submodule is pinned to a specific commit, giving you reproducible builds. Used heavily in large organizations for shared libraries.

bash
1# Add a submodule 2git submodule add https://github.com/org/lib.git libs/ui-kit 3 4# Initialize and clone submodules after cloning parent repo 5git submodule update --init --recursive 6 7# Update all submodules to their latest 8git submodule update --remote --merge 9 10# Clone repo AND all submodules at once 11git clone --recurse-submodules https://github.com/org/main-repo.git 12 13# Remove a submodule (multi-step process) 14git submodule deinit -f libs/ui-kit 15git rm -f libs/ui-kit

Resolving Merge Conflicts
Conflicts

Conflicts occur when two branches modify the same part of a file differently. Git pauses and asks you to choose which version to keep. Knowing how to confidently resolve conflicts is a must-have skill.

conflict markers in a file
<<<<<<< HEAD const greeting = "Hello World"; // YOUR version ======= const greeting = "Hi there!"; // INCOMING version >>>>>>> feature/greetings
bash — conflict resolution workflow
1# See all conflicted files 2git status 3 4# Open in VS Code to visually resolve 5code src/app.js 6 7# Use a mergetool 8git mergetool 9 10# Accept ALL current (ours) changes — e.g. during rebase 11git checkout --ours src/app.js 12 13# Accept ALL incoming (theirs) changes 14git checkout --theirs src/app.js 15 16# After manually editing — mark as resolved 17git add src/app.js 18git merge --continue # or git rebase --continue

🔥 Pro Level

The tools and strategies used by principal engineers, open-source maintainers, and DevOps professionals. Master these and you'll be in the top 1% of Git users.

🌲
git worktree
Multi-Branch Work

Allows you to check out multiple branches simultaneously in different directories from the same repository. Essential when you need to hotfix production while continuing feature work — without stashing or committing half-done work.

bash
1# List all worktrees 2git worktree list 3 4# Add a new worktree for a branch 5git worktree add ../hotfix-dir hotfix/critical-bug 6 7# Add a new worktree AND create the branch 8git worktree add -b hotfix/v2-security ../v2-fix 9 10# Remove a worktree when done 11git worktree remove ../hotfix-dir 12 13# Prune stale worktree references 14git worktree prune
🔥 Real-World Use Case

You're deep in a complex feature (100 file changes, not ready to commit). Suddenly there's a critical security bug on main. Instead of stashing everything, create a worktree: git worktree add ../critical-fix main. Fix the bug in ../critical-fix and push. Your feature directory is completely untouched.

🔬
git filter-repo
History Rewrite

The modern, fast replacement for git filter-branch. Used to rewrite git history at scale — removing sensitive files, extracting subdirectories into separate repos, or anonymizing history. Must-know for open-source maintainers.

bash
1# Install (pip-based) 2pip install git-filter-repo 3 4# REMOVE a sensitive file from ENTIRE history 5git filter-repo --path secrets.env --invert-paths 6 7# Extract a subdirectory into its own repo 8git filter-repo --subdirectory-filter packages/ui 9 10# Replace all occurrences of a string in history 11git filter-repo --replace-text replacements.txt 12 13# Remove all files larger than 10MB from history 14git filter-repo --strip-blobs-bigger-than 10M
⚠️
Nuclear Operation: filter-repo rewrites all commit hashes. Every collaborator must re-clone the repository. Always create a backup clone before running, and rotate any exposed secrets immediately.

Git Hooks
Automation

Scripts that Git automatically runs before or after events like commits, pushes, and merges. Used for enforcing code quality, running tests, checking commit message format, preventing pushes to protected branches, and more.

bash — hooks location
# Hooks live in: .git/hooks/ # Create a pre-commit hook (runs lint before every commit) # File: .git/hooks/pre-commit (must be executable) #!/bin/bash npm run lint if [ $? -ne 0 ]; then echo "❌ Lint failed! Fix errors before committing." exit 1 fi
bash — commit-msg hook (conventional commits)
#!/bin/bash # File: .git/hooks/commit-msg MSG=$(cat "$1") PATTERN='^(feat|fix|docs|style|refactor|test|chore)(\(.+\))?: .{1,72}' if ! echo "$MSG" | grep -qE "$PATTERN"; then echo "❌ Invalid commit message format!" echo "✅ Use: feat(scope): description" exit 1 fi
bash — using Husky (team-shareable hooks)
# Install Husky (hooks work for the whole team) npm install --save-dev husky npx husky init # Add pre-commit hook echo "npm run lint" > .husky/pre-commit # Add pre-push test runner echo "npm test" > .husky/pre-push
Hook NameWhen It FiresCommon Use
pre-commitBefore commit is createdLint, format check
commit-msgAfter message enteredValidate commit format
pre-pushBefore push to remoteRun tests
post-mergeAfter a merge finishesnpm install, migrations
pre-rebaseBefore rebase startsSafety checks

Git Aliases
Productivity

Custom shortcuts for frequently used Git commands. Senior engineers often have dozens of aliases that save hundreds of keystrokes per day. These are the aliases most commonly found in professional ~/.gitconfig files.

~/.gitconfig — professional aliases

git blame
Code Archaeology

Shows who last modified each line of a file, and when. Despite the name, it's used for understanding context — why a line was written the way it was, or who to ask about a piece of code. VS Code's GitLens extension makes this visual.

bash
1# Blame an entire file 2git blame src/auth.js 3 4# Blame a specific line range (lines 50-80) 5git blame -L 50,80 src/auth.js 6 7# Compact format (just hash, author, date) 8git blame -s src/auth.js 9 10# Ignore whitespace changes in blame 11git blame -w src/auth.js 12 13# Show blame at a specific commit 14git blame abc1234 -- src/auth.js 15 16# Search history for when a specific string was added 17git log -S "function authenticate" --oneline

Signing Commits (GPG/SSH)
Security

Cryptographically sign your commits and tags to prove they genuinely came from you. GitHub shows a ✅ Verified badge on signed commits. Required in many enterprise environments for security compliance.

bash — GPG signing setup
1# Generate a GPG key 2gpg --full-generate-key 3 4# List your GPG keys 5gpg --list-secret-keys --keyid-format=long 6 7# Export your public key (add this to GitHub Settings) 8gpg --armor --export YOUR_GPG_KEY_ID 9 10# Configure git to use your GPG key 11git config --global user.signingkey YOUR_GPG_KEY_ID 12 13# Sign every commit automatically 14git config --global commit.gpgsign true 15 16# Sign a single commit manually 17git commit -S -m "feat: signed commit" 18 19# Sign a tag 20git tag -s v1.0.0 -m "Signed release v1.0.0" 21 22# Verify a commit's signature 23git verify-commit abc1234
💡
Modern Alternative: GitHub now supports SSH-signed commits! If you already have an SSH key, you can sign with it: git config --global gpg.format ssh. Much simpler than GPG setup.

git sparse-checkout
Partial Clone

Allows you to check out only a subset of a repository's files. Critical for monorepos — when you only need the packages/frontend folder from a 50GB repo, you don't need to download all 50GB.

bash
1# Initialize sparse checkout 2git sparse-checkout init --cone 3 4# Set which directories to include 5git sparse-checkout set packages/frontend shared/utils 6 7# See what's currently included 8git sparse-checkout list 9 10# Add more paths 11git sparse-checkout add packages/api 12 13# Disable sparse checkout (restore everything) 14git sparse-checkout disable 15 16# Clone with sparse checkout from the start 17git clone --filter=blob:none --sparse https://github.com/org/monorepo.git 18cd monorepo 19git sparse-checkout set packages/frontend

git bundle
Offline Transfer

Packages a repository (or parts of it) into a single portable file. Useful for transferring git history in air-gapped (offline) environments, backups, or sending a repo via email/USB when there's no network access.

Git Flow Strategy
Branching Model

A structured branching model popularized by Vincent Driessen. Uses dedicated branches for features, releases, hotfixes, and development. Well-suited for projects with versioned releases (e.g., mobile apps, desktop software, npm libraries).

git flow branch structure
main # Production-ready code. Always deployable. develop # Integration branch. Latest dev snapshot. # Feature branches (from develop) feature/user-auth feature/payment-api # Release branches (from develop, merge to main+develop) release/v2.0.0 # Hotfix branches (from main, merge to main+develop) hotfix/critical-login-bug
bash — git flow commands
# Install git-flow tool # macOS: brew install git-flow-avh # Windows: git-flow is bundled with Git for Windows # Initialize git flow in a repo git flow init # Start a new feature git flow feature start user-authentication # Finish a feature (merges to develop) git flow feature finish user-authentication # Start a release git flow release start 2.0.0 # Finish release (merges to main AND develop, creates tag) git flow release finish 2.0.0 # Start a hotfix git flow hotfix start critical-null-fix # Finish hotfix (merges to main AND develop) git flow hotfix finish critical-null-fix

Trunk-Based Development
Modern Strategy

The branching strategy used by Google, Meta, Netflix, and most high-velocity engineering teams. Everyone commits to main frequently (multiple times per day) using short-lived feature branches. Enables continuous integration and rapid deployment.

bash — trunk-based workflow
1# Branches are SHORT-LIVED (hours to max 2 days) 2git switch -c feature/quick-fix # from main 3 4# Make small, focused changes 5git commit -m "feat: add email validation" 6 7# Rebase on main before PR (keep linear) 8git fetch origin 9git rebase origin/main 10 11# Push and immediately create PR 12gh pr create --fill 13 14# Use Feature Flags for incomplete features 15# so code can merge to main even if not ready for users 16if (featureFlags.NEW_CHECKOUT_FLOW) { 17 // new code — hidden behind a flag 18}

Export

Creates a snapshot of your repository's files at a specific commit or tag, compressed into a zip or tar archive — without the .git directory. Perfect for distributing source code releases or creating deployable artifacts.

bash
